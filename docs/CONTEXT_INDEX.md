> Context routing only. Current implementation/commit facts: FEATURE_LEDGER and PROJECT_STATUS. Current priorities: NEXT_ACTIONS.

## Session and task reading route

1. Read `START_HERE.md`, `AGENTS.md`, `RULES.md`, `docs/NEXT_ACTIONS.md`, and `docs/technical/AGENT_EXECUTION_CONTRACT.md`; inspect current Git state and existing owner scope.
2. Read the active task entry in `docs/implementation/FEATURE_LEDGER.md` and `docs/PROJECT_STATUS.md` when current implementation evidence matters. Use `docs/MASTER_PROJECT_PLAN.md` and `docs/ROADMAP.md` for milestone questions.
3. Load applicable `docs/DECISIONS.md` entries, TD ownership/approval/gate sections, and domain specs using the routing table below. Load `docs/pipelines/ARGON_NATIVE_ASSET_PROFILE.md` only for art/capability work. A docs/tooling review does not need all gameplay/art specs reread.
4. Select only relevant skills using `docs/technical/AGENT_SKILL_ROUTER.md`. Preserve already-read unchanged context across turns. Full historical Phase 0 / Phase 1A documents live under `docs/archive/legacy/*` (with short locator stubs at `MASTER_PROMPT.md`, `docs/CONTEXT_AUDIT.md`, and `docs/IMPLEMENTATION_STATUS.md`, while `EXTERNAL_SKILLS.md` and `docs/WORKSPACE_HANDOFF.md` have been removed from the active tree); treat archived files strictly as historical evidence, never current task instructions.

**Conflict policy**: Safety/canon boundaries remain highest (`AGENTS.md` Section 1). Owner-approved gameplay decisions in `docs/DECISIONS.md` and technical scope approvals in `docs/technical/TD_FREEZE_APPROVALS.md` override historical gameplay/bootstrap instructions and conflicting third-party skill defaults where explicitly inconsistent. `packages/game-data/src/catalogs/*`, `packages/game-data/src/rules/*`, and `packages/game-data/src/index.ts` represent current implementation data (mixing `S1` `Character v0.2` catalogs/rules with retained `v0.1` prototype data), not automatic approval of outdated `v0.1` mechanics. Never erase canonical IDs or make undocumented lore changes.
